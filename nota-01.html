Nota 01

O abismo entre o teste e a produção

📅 29 de setembro de 2026 ⏱️ 7 min de leitura
Produção Linux Cron Python Cloudflare API

O que eu construí

Meu IP de saída muda. Quando isso acontece, qualquer coisa que dependa de um nome apontando para a minha casa deixa de responder. Então escrevi o myDDNS, uma aplicação em Python que resolve isso sozinha: ela descobre o meu IP público, compara com o último conhecido e, se mudou, atualiza o registro DNS na Cloudflare e me avisa por e-mail.

Parece pouco, mas o problema tem várias peças: consumo de API (para descobrir o IP, falar com a Cloudflare e enviar o e-mail), estado persistido em arquivo entre execuções, agendamento com cron e, no fim, um servidor rodando tudo sem ninguém olhando. Fiz o projeto sem dependências externas, só módulos nativos do Python, justamente para simplificar o deploy.

"Mas é o mesmo sistema operacional"

Desenvolvi e testei tudo no meu computador, que roda Ubuntu. O servidor onde a aplicação ia viver também roda Ubuntu. Eu estava tranquilo: mesma distribuição, mesmos comandos, mesmo shell. A distância entre fabricação e produção, pensei, era mínima.

Não era. E o mais interessante é que quanto mais parecidos os ambientes, mais perigosa é a confiança. Com sistemas muito diferentes você já espera problemas. Com dois Ubuntu, você deixa de checar as premissas.

O abismo não estava no sistema operacional. Estava em tudo o que eu tinha assumido sem perceber.

O dia do deploy, commit a commit

O histórico do repositório conta essa história melhor do que a minha memória. Foram sete correções em um único dia (27/07), todas para fazer funcionar em produção o que já funcionava no meu computador:

  1. Variáveis não inicializadas

    Se a leitura do .env falhava, o bloco de tratamento de erro tentava usar variáveis que nem existiam e estourava um UnboundLocalError. Solução: inicializar tudo antes do try.

  2. Caminhos que dependiam de onde eu estava

    Dois commits para resolver a mesma raiz: o cache e o .env eram abertos por caminho relativo. No terminal, dentro da pasta do projeto, funcionava. Fora dela, não. A correção foi resolver o diretório a partir do próprio arquivo, com Path(__file__).resolve().parent.

  3. Shebang

    Adicionei #!/usr/bin/env python3 ao topo do myDDNS.py para o script poder ser executado direto, como o agendador faz.

  4. O cache "sumia"

    A mensagem do commit resume: "o local do sudo cron é diferente do local do cache". O teste de existência do arquivo de cache ainda usava caminho relativo, então o cron não o encontrava, achava que sempre era a primeira execução e atualizava tudo de novo.

  5. O erro dentro do tratamento de erro

    Se o envio do e-mail de alerta falhasse, dentro do tratamento de outra falha, nada capturava essa segunda exceção. Envolvi o envio em um novo try/except.

Onde quebrou

Olhando para trás, os problemas cabem em três famílias. Todas com a mesma raiz.

🔐

Permissões

No meu computador eu sou o dono de tudo. No servidor, cada coisa tem dono, grupo e modo. Quem executa a aplicação, quem lê o .env e quem escreve o cache deixaram de ser a mesma pessoa.

Lição: teste como o usuário que vai executar de verdade.
🗺️

Paths e falta de dinamismo

Caminhos que funcionavam por acaso, relativos ao diretório onde eu estava. O cron, rodando via sudo, tem outro diretório de trabalho, e cada arquivo aberto do jeito antigo virou uma falha.

Lição: o cron não é o seu terminal.
🪞

O erro que esconde o erro

Uma falha ao ler o .env virava outra falha no tratamento, e uma falha no e-mail de alerta virava uma terceira, sem ninguém para capturar. O tratamento de erro também é código que precisa de teste.

Lição: o caminho de erro precisa ser testado como o caminho feliz.

Mesmo Ubuntu, premissas diferentes

Aspecto Meu ambiente de teste Servidor de produção
Quem executa Eu, em sessão interativa Cron via sudo, sem sessão nem terminal
Permissões Sou dono de tudo Dono, grupo e modo importam
Diretório atual A pasta do projeto Definido pelo agendador
Caminho do cache e do .env Relativo, funciona por acaso Precisa ser resolvido a partir do próprio script
Quando dá erro Vejo na hora, na tela Ninguém vê, a menos que exista registro

A correção que mais se repetiu

Trocar "o arquivo que está aqui, onde eu estou" por "o arquivo que está ao lado do código". Em cache.py:

cache.py
# diretório base absoluto do módulo, resolvido a partir do próprio arquivo
+ DIRETORIO = Path(__file__).resolve().parent

- with open(NOME_ARQUIVO, 'r', encoding='utf-8') as arquivo:
+ caminhoAbsoluto = DIRETORIO / NOME_ARQUIVO
+ with open(caminhoAbsoluto, 'r', encoding='utf-8') as arquivo:

Uma linha de diferença, e a aplicação deixa de depender de onde foi chamada.

🧭

O que levo para os próximos projetos

Checklist Produção
  • Explicitar tudo o que hoje é implícito: usuário, diretório, caminhos e variáveis;
  • Resolver caminhos a partir do próprio código, nunca de onde a aplicação foi chamada;
  • Separar configuração e segredos do código, com permissões restritas ao usuário que os usa;
  • Testar como o usuário que vai executar, do jeito que vai executar;
  • Testar também o caminho de erro, não só o caminho feliz;
  • Ensaiar o deploy em um ambiente o mais próximo possível do real, antes do real.

O que ficou

Ter um servidor doméstico ajudou a enxergar isso com clareza, porque o erro é meu e o conserto também. A lição principal não é técnica: "funciona na minha máquina" descreve a máquina, não a aplicação.

Produção não é um lugar onde o código roda. É um lugar onde cada premissa não declarada vira uma falha. A distância entre teste e produção nunca é zero, mas ela pode ser conhecida, e conhecê-la é o trabalho.
